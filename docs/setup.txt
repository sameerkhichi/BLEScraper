BLEScraper setup
=================

This app runs on an iPhone. It reads the Colmi R09 over unencrypted BLE GATT, keeps the reading on the phone if the network is down, and POSTs JSON to an HTTP API. That API is the Arduino Uno Q, reached through your home network and port forwarding.

The iOS binary is built in the cloud with EAS, uploaded to App Store Connect, and attached to the TestFlight group named Internal. GitHub Actions does that on every push to main that changes code, and again on the 1st of every other month so the TestFlight build is refreshed before the 90-day expiry. GitHub's scheduler has no "every 60 days" interval, so every other month is the schedule.

FOR API/IP FORWARDING USAGE.
The Arduino URL, entered in the app under Settings.
Example: http://203.0.113.10:8080/ingest
   The phone allows plain HTTP because the home server is not required to have a certificate.
   Optional API key is sent as the X-Api-Key header.
   Config, on the Arduino card, chooses Raw, Processed, or Both. Raw is the sample JSON below. Processed sends the averages, scores, and debts. Both sends the sample JSON and that summary. Today, This week, and All limit the summary. The field list is in docs/BLEScraper.txt under Sending to the Arduino IP.


Install
-------

Node 22.14 or newer.

    npm ci

Dependencies are declared in package.json and locked in package-lock.json. requirements.txt in the repo root is the same direct dependency list.

Day-to-day JS check, from Windows:

    npm test
    npm run typecheck
    npx expo start

Bluetooth is a native module, so Expo Go cannot talk to the ring. A development or TestFlight build is required on the phone. This PC cannot compile the iOS app locally. EAS builds it.

First production cloud build
-----------------

    npx eas-cli login (verifies user credentials)
    npx eas-cli init (initializes production and writes project id)
    npx eas-cli build --platform ios --profile production (creates a cloud build)

The first build asks Apple credential questions and saves them for the GitHub Action. 
After it finishes:

    npx eas-cli submit --platform ios --profile production --latest

eas.json does not contain the App Store Connect app id or the Apple Team ID. EAS cannot read those two fields from environment variables. For a local submit, set ASC_APP_ID and APPLE_TEAM_ID in the shell, run node scripts/write-submit-ids.mjs, then submit. Do not commit the eas.json change that script makes.

Confirm the build shows up in TestFlight and installs on the phone. Later pushes to main do this from GitHub Actions.

GitHub Action
-------------

Workflow: .github/workflows/testflight.yml

Repository secrets, used only on the GitHub runner:

    EXPO_TOKEN
    ASC_APP_ID
    APPLE_TEAM_ID

The job writes the two Apple ids into its checkout of eas.json, then runs `eas build --platform ios --profile production --auto-submit`. That copy of the file is discarded with the runner. EAS builds the IPA, then submits it to TestFlight when the build finishes. The action does not wait for the compile, so GitHub minutes stay short. You can also run it by hand from the Actions tab.

Scheduled runs only happen from the default branch, which is main.

What the phone sends
--------------------

POST the saved API URL with Content-Type application/json. The Arduino card chooses Raw, Processed, or Both. Raw is the body below. Processed and Both are described in docs/BLEScraper.txt. A URL has to start with http:// or https://, including an IP address. A blank URL or a failed response keeps the reading on the phone.

    {
      "source": "colmi-r09",
      "syncedAt": "2026-11-06T19:45:00.000Z",
      "ring": { "id": "ios-peripheral-uuid", "name": "R09" },
      "battery": { "level": 64, "charging": false },
      "realtimeHeartRate": null,
      "spo2": 98,
      "bodyTemperatureC": 36.6,
      "vitalSpots": [
        { "timestamp": "2026-11-06T19:45:00.000Z", "spo2": 98, "bodyTemperatureC": 36.6 }
      ],
      "heartRate": [{ "timestamp": "2026-11-06T19:40:00.000Z", "bpm": 72 }],
      "steps": [{ "timestamp": "2026-11-06T19:30:00.000Z", "steps": 120, "calories": 8, "distanceMeters": 90 }],
      "warnings": []
    }

Any HTTP status from 200 through 299 removes that reading from the phone queue. Anything else keeps it, in order, and the next sync or app launch tries again.

The ring clock is set to UTC on each sync. Heart-rate history is 5-minute samples. Step history is 15-minute blocks. A sync reads yesterday and today. "Measure heart rate" takes a live reading and sends that on its own.

Automatic sync
--------------

Heart rate interval and the blood oxygen, stress, and HRV switches live on the ring. Settings is at the top right of the home screen. Opening it reads those values. Heart rate can be 5, 15, 30, or 60 minutes. Blood oxygen, stress, and HRV are on/off only. The firmware picks their cadence: stress about every 30 minutes, HRV about every 60, blood oxygen about hourly, and skin temperature about every 30. A download does not rewrite them. Connecting again reads whatever the ring still has. The phone copy is the last successful read. The gesture switch is the ring's saved on/off. A download does not change it. What a wave does on the phone comes from an iOS Bluetooth bond, not from that switch. SpO2 and temperature come back as half-hour slots.

With a ring selected, the iPhone checks for ring data when iOS allows background activity, even when the screen is locked and the app is not on screen. That depends on scheduling, settings, battery, and how the phone is used. A wake sends waiting readings first, then downloads stored heart rate, steps, sleep, blood oxygen, temperature, stress, and HRV when the ring is nearby, and disconnects. It does not start a live sensor reading. The ring can be on the table. A short wake reads about 2 days. The overnight wake reads about a week, so a missed wake does not drop a day inside that week. Opening the app still waits 4 hours after the last saved download.

iOS chooses the actual time. Keep syncing arms the first request. The next refresh is submitted when a wake starts, before the ring is contacted. A normal open does not replace a request that is already pending. The download does not wait for Wi-Fi. Settings chooses a notice after a saved download, after a successful send, or either, and the switch turns those notices off. Leaving the app in the switcher does not promise a wake, and swiping it away can stop the next one until you open the app again. Android shows a notification only while a download is running, and it keeps its existing scheduler.

Leaving the app open does not start a repeating heart-rate, blood-oxygen, or temperature check. Opening the app runs a download when one is due. The Measure buttons run only when tapped. Turn the wakes off under Settings, Keep syncing.

This needs a new development or TestFlight build. Background Bluetooth and the scheduler are native, so Expo Go cannot run them.

The GATT service is 6E40FFF0-B5A3-F393-E0A9-E50E24DCCA9E. Writes go to 6E400002 and notifications come from 6E400003. Packets are 16 bytes. Sleep and the larger stored logs use DE5BF728-D711-4E47-AF26-65E3012A5DC7, notify DE5BF729 and write DE5BF72A. The iOS build discovers only those two services and those four characteristics. It does not read or write any other attribute. iPhone shows a Pair sheet only for Insufficient Authentication, so this connect does not create a bond and iOS does not load HID. Forget the ring in Bluetooth Settings once. A bond already saved there keeps delivering media keys until it is forgotten. Without that bond, media apps ignore the ring's gesture keys. The Settings gesture switch only reads and writes the ring's saved on/off. It does not choose what a wave does, and a download does not change it.
